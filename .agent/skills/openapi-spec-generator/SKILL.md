# OpenAPI 3.1 Specification Generator

This skill defines the mandatory procedure for authoring OpenAPI 3.1 YAML specifications for backend services running on Google Cloud Run. All API contracts must strictly conform to OpenAPI 3.1 standards, utilize RFC 7807 problem details for error responses, and pass automated schema validation before implementation begins.

## Prerequisites
- Python 3.11+ installed locally or in CI/CD.
- `ruamel.yaml` installed (`pip install ruamel.yaml` or via Poetry/uv).
- Understanding of HTTP/1.1 and HTTP/2 REST semantics and GCP Cloud Run ingress requirements.

## Step-by-Step Procedure

### Step 1: Define API Metadata and Server URLs
Every specification must declare `openapi: 3.1.0`, concise API metadata, and target server URLs representing local development, staging, and production environments.

```yaml
openapi: 3.1.0
info:
  title: Cloud Backend Service API
  description: Production-grade REST API deployed on GCP Cloud Run.
  version: 1.0.0
  contact:
    name: GCP Solutions Architect
    email: architect@example.com
servers:
  - url: https://staging-api-service-uc.a.run.app/v1
    description: GCP Staging Cloud Run Environment
  - url: https://api-service-uc.a.run.app/v1
    description: GCP Production Cloud Run Environment
```

### Step 2: Define Paths and Operations
Define discrete REST endpoints with explicit HTTP methods (`get`, `post`, `put`, `delete`). For each operation:
1. Assign a unique `operationId` in `camelCase` (e.g., `listUsers`, `createOrder`).
2. Provide concise `summary` and `description` fields.
3. Define request parameters (path, query, header) with strict schemas and descriptions.
4. Specify request bodies using `application/json` content type and JSON Schema references.

### Step 3: Implement RFC 7807 Error Responses
All 4xx and 5xx error responses MUST reference the standard RFC 7807 problem detail schema located in `templates/standard_error_response.yaml` or defined within the document's `components/schemas`.

Do not invent custom error structures. Every error response must return:
- `type`: A URI reference identifying the problem type.
- `title`: A short, human-readable summary of the problem type.
- `status`: The HTTP status code generated by the origin server.
- `detail`: A human-readable explanation specific to this occurrence of the problem.
- `instance`: A URI reference that identifies the specific occurrence of the problem.

### Step 4: Validate the Specification
Before finalizing any specification or opening a pull request, run the syntax and schema validator script:

```bash
python .agent/skills/openapi-spec-generator/scripts/validate_yaml.py --file path/to/api-spec.yaml
```

## Verification & Troubleshooting

### Verification Command
To verify that an OpenAPI YAML document is structurally valid and contains required RFC 7807 schemas:

```bash
python -m ruamel.yaml --check path/to/api-spec.yaml
```

### Common Errors and Solutions
- **Error: `Missing required property: openapi`**
  - *Solution*: Ensure the document header starts with `openapi: 3.1.0` (not `3.0.0` or `3.0.3`).
- **Error: `Invalid schema type in OpenAPI 3.1`**
  - *Solution*: OpenAPI 3.1 natively uses JSON Schema Draft 2020-12. Use `null` as a type or `anyOf`/`oneOf` for nullable fields instead of OpenAPI 3.0's `nullable: true`.
- **Error: `RFC 7807 schema compliance failure`**
  - *Solution*: Ensure error responses reference `#/components/schemas/ProblemDetails` and include `status` and `title` fields.
